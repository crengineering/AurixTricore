# BMP581.md — Bosch BMP581 barometer, wiring & bring-up

**ASPICE:** SWE.3 — driver detailed design + bring-up evidence · supports SYS1-010, SYS2-NAV-001 · process: QuadSE/requirements/README.md

Wiring and bring-up notes for the **BMP581** on **I2C0**, replacing the BMP388
(CJMCU-388) and the MPU-6050 (GY-521), both removed 2026-07-31.

**Board: Adafruit BMP581 STEMMA QT breakout.** This matters — the Adafruit
board resolves two of the three traps this document originally warned about,
and it changes the I2C address (§4). Photographed and confirmed 2026-08-01.

> **Pin-allocation SSoT:** the authoritative MCU-side pin map is
> **[PINNING.md §2.3](PINNING.md)** (I2C0 SCL/SDA) and **§2.5** (electrical). This file
> covers the *breakout side* and does not allocate MCU pins.

Driver: `src/bsw/Bmp581.{c,h}`, integrated in firmware **v1.14.0**.

> ✅ **HARDWARE-VALIDATED 2026-08-01** — 954.60 hPa / 27.80 °C / 500.1 m, values
> moving in the 4th digit every sample, `diagStatus` clear of all baro, I2C and
> IMU bits. Cross-checks against the BMP388's 956 hPa / 26.8 °C / 484 m from
> 2026-07-30 (1.4 hPa ≈ 12 m accounts for the altitude difference).
> The driver was written from the BMP5 register map **without the datasheet in
> hand**; §7.2 records the known-good boot dump that confirmed every assumption.

## 1. Wiring — four wires, no new MCU pins

The BMP581 joins the same two pins the BMP388 used. Nothing on the MCU side
changes, so `I2c.c` needs no edit at all.

```
   +3V3 rail (X702·78/80 or X703·70) ─────────── VIN
   GND (X702·1-4 etc.)               ─────────── GND
   TC399 P13.1  SCL (X702·29)        ─────────── SCL
   TC399 P13.2  SDA (X702·35)        ─────────── SDA
```

| Breakout pad | Wire to | Header · pin | iLLD object |
|---|---|---|---|
| VIN | **+3V3** (see §2) | X702·78 or ·80, X703·70 | — |
| GND | GND | X702·1–4, 37, 38 … | — |
| SCL | **P13.1** | X702·**29** | `IfxI2c0_SCL_P13_1_INOUT` |
| SDA | **P13.2** | X702·**35** | `IfxI2c0_SDA_P13_2_INOUT` |
| 3Vo | **leave open** | — | regulator *output*, not an input |
| CS | leave open | — | strapped high on-board, §3 |
| INT | leave open | — | polled at 50 Hz |

The two STEMMA QT connectors carry the same SCL/SDA/3V3/GND and are simply an
alternative to soldering the header — either is fine.

**Four wires really are enough — CS and SDO stay open.** The proof is the
STEMMA QT connector itself: it carries only GND, 3.3 V, SDA and SCL, and the
board is sold to work over that cable alone. CS and SDO must therefore already
be strapped on-board, or no STEMMA QT cable could ever bring the part up in I2C
mode. Soldering the four header pins is electrically the same connection.

**SDO is not a header pin on this board.** The pads are `VIN, 3Vo, GND, SCL,
SDA, CS, INT`; the address is set by the `addr` solder jumper on the back
(§4), not by a wire.

## 2. Power — +3V3

The silkscreen reads **`VLogic/Vcc: 3-5VDC`**: the board has an onboard
regulator and level shifting, so 5 V on VIN would not damage it. Use the
board's regulated **+3V3** rail anyway — the bus then sits at a clean 3.3 V
that the TC399's TTL-mode pads read reliably, with no level translation in the
signal path to reason about.

`3Vo` is the regulator's **output**. Leave it unconnected.

---

## 3. CS — already strapped high (no action)

The BMP581 die selects its interface from CS: **high = I2C, low = SPI**, and a
floating CS is the classic reason a correctly wired sensor never ACKs. On the
BMP388 this bit us exactly that way.

**The Adafruit board pulls CS high for you**, which is why its silkscreen
advertises `(SPI/I2C)` with I2C as the default, and why a 4-wire STEMMA QT
cable is sufficient (§1). Leave the CS pad open — that is its strapped state,
not a floating input.

If the first CHIP_ID read fails, this is still worth a meter check (CS pad to
VIN should read a pull-up, not open) before suspecting anything else.

## 4. ⚠️ Address — `0x47` on this board, not `0x46`

| SDO / addr jumper | 7-bit address |
|---|---|
| **as shipped** (SDO strapped high) | **`0x47`** ← driver default |
| `addr` jumper moved (SDO low) | `0x46` |

The back of the board says **`Default I2C addr 0x47`**. This is the opposite of
the bare-die default, and the driver originally had `0x46` — corrected in
v1.14.0. `BMP581_I2C_ADDR` in `Bmp581.h` is now `0x47`.

If the bring-up read fails, try `0x46` before suspecting anything else — it is
one `#define` and costs nothing.

No collision with the planned MMC5983MA (`0x30`) or NEO-M9N (`0x42`), and
nothing carries over from the BMP388's `0x77`.

## 5. Pull-ups — provided by the breakout

Until 2026-07-31 the bus was held up by **two** breakouts in parallel — the
CJMCU-388's ~10 kΩ and the GY-521's ~4.7 kΩ, about **3.2 kΩ** combined.
Removing both removed all of it, so whatever the BMP581 board carries is now
the entire bus.

**STEMMA QT boards carry 10 kΩ pull-ups on SDA and SCL**, so this should be
handled. 10 kΩ alone is weaker than the old 3.2 kΩ but comfortable at the
100 kHz this bus runs at.

Confirm it rather than assume it — the firmware prints exactly this at boot:

```
I2C0 bus idle (SCL+SDA released)      <- good
I2C0 bus HELD - a slave is pulling SCL/SDA low
```

A bus with *no* pull-ups never idles high and nothing ACKs, which looks exactly
like a dead sensor. If that happens, add 4.7 kΩ from SCL and SDA to +3V3.

## 6. Firmware — what changed in v1.14.0

1. `Cpu0_Main.c` — `Task_Baro` now calls `Bmp581_read()`. `Task_Imu`, the
   MPU-6050 init and `mpuDebugDump()` are gone; `bmp581DebugDump()` replaces
   the latter. `publishNoImu()` writes the IMU fields once at start-up so they
   read zero rather than whatever RAM powered up with. (The attitude fields it
   also wrote were removed with the estimator on 2026-08-22; attitude returned
   on 2026-08-26 in `Ahrs.c` and is now published in its own `Xcp_Fusion` block
   — see `docs/FUSION.md`.)
2. `PeriphDiag` — new `PeriphDiag_setFitted()`. Peripherals now start
   **unfitted** and the build declares what it expects; an unfitted slot
   contributes no `diagStatus` bits. Without it the empty IMU slot would assert
   `IMU_NO_RESPONSE` forever and leave the diagnostics permanently red. This is
   also the hook the planned driver pool needs: *which devices are connected is
   configuration, not a compile-time fact about the code.*
3. `Bmp388.c/h` and `Mpu6050.c/h` are **kept in the tree** as the start of the
   driver pool, with **no caller at all** — see §9. (`Ahrs.c/h` was deleted on
   2026-08-22 and rewritten from scratch on 2026-08-26 as a quaternion Mahony
   estimator; it is a live caller again, not part of the pool.)
4. `docs/AurixTricore.a2l` — `Baro*` descriptions renamed to BMP581 (addresses
   unchanged); `Imu*` descriptions made sensor-neutral and marked unfitted.

## 7. Bring-up order — do these one at a time

Skipping straight to "read the data" hides which layer is broken. In order:

### 7.1 Bus idle
Boot and look for `I2C0 bus idle` on the UART. If it says HELD, stop — that is
§5 or a short, and nothing else will work.

### 7.2 CHIP_ID and the boot dump
`Bmp581_init()` prints one of:

```
BMP581 detected (CHIP_ID 0x50/0x51)
BMP581 not found - check wiring/address (0x47 default, 0x46 via addr jumper)
```

That one transaction proves pins, pads, pull-ups, address, CS strap and driver
together. The driver accepts **`0x50` or `0x51`** — the BMP5 family ships both
IDs. (`0x50` is also the BMP388's ID; the two are told apart by address, not by
this register.)

Immediately after, `bmp581DebugDump()` prints:

```
BMP581 CHIP/REV/INT_STAT/STAT/IIR/OSR/ODR=50 xx 10 02 22 61 BD OSR_EFF=xx burst(T,P)=...
```

**This dump is the point of the whole exercise** — every register value in
`Bmp581.c` was written from the BMP5 register map without the datasheet, so
this is where those assumptions meet silicon. Read it in this order:

Measured on hardware 2026-08-01 (this is a known-good reference dump):

```
BMP581 CHIP/REV/INT_STAT/STAT/IIR/OSR/ODR=50 32 10 01 22 61 BD OSR_EFF=A1 burst(T,P)=7F 7F 7F 7F 7F 7F
```

| Field | Expect | If wrong |
|---|---|---|
| `CHIP` | `0x50` (or `0x51`) | wrong address, or not a BMP581 |
| `INT_STAT` bit 4 | `1` (por_softreset_complete) | the soft reset did not land. Clear-on-read, so only the **first** dump after init shows it |
| `STAT` bit 0 | `1` (core_rdy) | see the note below — do **not** look for nvm_rdy here |
| `OSR` bit 6 | `1` (press_en) | pressure is not being converted; this is why a device reads a sane temperature next to a pressure register that never moves |
| `ODR` bits 1:0 | `1` (normal mode) | not converting |
| `OSR_EFF` bit 7 | `1` (odr_is_valid) | 50 Hz is too fast for 16× pressure oversampling and the device quietly reduced the effective OSR — signal is noisier than configured, but working. `0xA1` decodes to odr_valid + 16×P + 2×T, i.e. exactly what was asked for |

⚠️ **`STAT` reads `0x01`, and that is correct.** `nvm_rdy` (bit 1) is set in
standby right after reset — which is where `Bmp581_init()` checks it, the only
place it means anything — and clear once the device is in normal mode, which is
where this dump runs. On 2026-08-01 init passed the trim check and the dump
still read `0x01` moments later. A genuine trim failure surfaces as
`Bmp581_init()` returning FALSE (→ `BMP581 not found`), never as a bit here.

⚠️ **An all-`0x7F` burst in the boot dump is normal.** The data registers hold
`0x7F7F7F` until the first conversion completes, and the dump runs within a few
ms of `ODR_CONFIG` starting them. The 50 Hz task read valid data immediately
afterwards. A burst that is *still* `0x7F` once the task is running, or one that
is identical across two resets, is the real fault — the device is not
converting, and that is not a scaling problem.

### 7.3 Plausibility
~954 hPa and ~484 m in Munich, matching what the BMP388 read on 2026-07-30 — a
direct cross-check against a known-good measurement.

### 7.4 Liveness
Confirm the value *changes*. `PeriphDiag` raises `BARO_STUCK_DATA` after 5 s of
a frozen reading; that check exists precisely because a sensor that ACKs
everything while its registers stand still cost two days and two wrongly
condemned chips.

## 8. Configuration the driver applies

| Register | Value | Meaning |
|---|---|---|
| `DSP_CONFIG` 0x30 | `0x0A` | shdw_sel_iir_t + shdw_sel_iir_p — route the **filtered** value into the data registers. Without these the filter runs but the burst read returns the raw sample |
| `DSP_IIR` 0x31 | `0x0A` | IIR coeff **1** on pressure, coeff 3 on temperature — see the warning below |
| `OSR_CONFIG` 0x36 | `0x61` | press_en, 16× pressure / 2× temperature oversampling |
| `ODR_CONFIG` 0x37 | `0xBD` | deep_dis, 50 Hz, normal mode |

> ⚠️ **`DSP_IIR` was `0x22` (pressure coeff 15) until 2026-08-26.** That is the
> BMP388 indoor-navigation preset and it is the wrong preset for a flight
> vehicle. The IIR is `y[n] = (c*y[n-1] + x[n])/(c+1)`, so at coeff 15 and 50 Hz
> it is an exponential average with a **~310 ms time constant** — and the Kalman
> filter downstream models no lag, so it treats that smoothed value as an
> instantaneous altitude.
>
> **Do not filter twice.** `OSR_p` averages within one conversion and has no
> memory, so it reduces noise for free; the IIR reduces noise by *remembering*,
> and that memory is the lag. Measured on this board, removing it moved the
> innovation-vs-vertical-velocity slope from **−0.0606 s to +0.0058 s** (the lag
> signature disappearing) for an 8 % noise cost.
>
> The noise barely rose because the barometer's apparent scatter is **real
> low-frequency pressure fluctuation, not sensor white noise** — so coeff 15 was
> paying 310 ms of lag for almost nothing. Full reasoning and the measurements
> are in `docs/FUSION.md` §8. Any change here invalidates `FUSION_SIGMA_BARO`,
> which is a *measured* constant — re-measure it.

The boot dumps in §7 below were captured with the old `0x22` value, so they show
`IIR=22`; a current board reads `IIR=0A`.

Two ordering constraints are not visible in the register map and are the usual
reason a BMP581 reads zeros or an unfiltered value:

1. **The DSP registers only accept writes in standby.** Soft reset leaves the
   device in standby, so all configuration happens *before* `ODR_CONFIG`
   switches it to normal mode — never after.
2. **`ODR_CONFIG` is written last**, because that write is what starts
   conversions.

Output scaling needs no compensation polynomial: the BMP581 calibrates on-chip,
so temperature = signed24 / 2¹⁶ °C and pressure = unsigned24 / 2⁶ Pa. That is
why this driver is ~250 lines against the BMP388's ~300 despite doing more
checking.

## 9. ⚠️ Open item: Bmp388.c and Mpu6050.c now have no caller

Both drivers stay in the tree on purpose (driver pool), but nothing calls them
any more. That is expected to trip **MISRA 8.7** — external linkage on a symbol
referenced in ≤ 1 translation unit — in the CI gate, which is exactly what kept
`Bmp581.c` untracked before this. It is **not** verifiable locally: cppcheck is
not installed on this machine, so `tools/misra_check.py` cannot run here.

The agreed fix is the **driver registration table**: one `PeriphDriver` table of
`{name, init, probe, read, enabled}` referencing every driver, so nothing is
dead to the linker or to cppcheck even when `enabled` is false, while runtime
configurability is preserved. `PeriphDiag_setFitted()` (§6.2) is the first piece
of it. Do not re-baseline the MISRA findings instead — `CLAUDE.md` is explicit
that new code should be fixed rather than grandfathered.

## 10. Datasheet

Not in the repo. The BMP581 register map differs from the BMP388 — notably it
returns **ready-scaled** pressure and temperature, so there is **no 21-byte NVM
trim block and no Bosch compensation polynomial** to port. Register addresses,
field layouts and the ODR/OSR encodings in `Bmp581.c` follow the map as
implemented by Bosch's BMP5 sensor API; §7.2 is how they get verified.
