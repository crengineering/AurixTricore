# MPU6050.md — GY-521 IMU wiring & bring-up

**ASPICE:** archive — superseded hardware (removed 2026-07-31), kept as evidence · process: QuadSE/requirements/README.md

Wiring and bring-up notes for the **GY-521** breakout (InvenSense **MPU-6050**
6-axis IMU: 3-axis gyro + 3-axis accelerometer) on the shared **I2C0** bus. It
is a borrowed stand-in for the delayed **ICM-42688-P** (the planned flight IMU,
which lives on QSPI0 — see `PINNING.md` §2.2). The MPU-6050 rides I2C instead
and shares the bus with the BMP388 barometer.

> **Pin-allocation SSoT:** the authoritative MCU-side pin map lives in
> **`PINNING.md` §2.2** (interim-IMU note), **§2.3** (I2C0 SCL/SDA) and **§2.5**
> (electrical). This file documents the *breakout side* and the board-to-sensor
> wiring; it does not re-allocate MCU pins.

Datasheet: `Quadrocopter/doc/gy-521_mpu-6050_3-axis_gyroscope_and_acceleration_sensor_en.pdf`
plus the InvenSense Register Map (RM-MPU-6000A, Rev 4.2).
Driver: `src/bsw/Mpu6050.c` / `.h`, initialised from `Cpu0_Main.c`, read at 50 Hz.

---

## 1. Why it just joins the existing bus (the pinning suggestion)

The BMP388 barometer already owns I2C0 on **P13.1 (SCL)** / **P13.2 (SDA)**. The
MPU-6050 is an I2C device at address **`0x68`**, which does not collide with the
BMP388's **`0x77`**. So the IMU **shares the same two pins** — **no new MCU pins
are allocated**. It needs only power, ground, and (optionally) its INT line:

```
                 +3V3 rail ──┬──────────────┬────────── VCC (both breakouts)
                             │              │
   TC399 P13.1 SCL ──────────┼──────┬───────┼───────── SCL  (BMP388 SCK / GY-521 SCL)
   TC399 P13.2 SDA ──────────┼──┬───┼───────┼───────── SDA  (BMP388 SDI / GY-521 SDA)
                             │  │   │       │
                          (pull-ups live on each breakout, to its VCC=3V3)
                             GND ─────────────────────  GND (both breakouts)

   BMP388 @ 0x77   ◄── same two wires ──►   MPU-6050 @ 0x68
```

This is the whole recommendation: **daisy-chain the GY-521 onto the BMP388's
SCL/SDA/3V3/GND.** The only electrical thing to check is bus loading (§3).

## 2. GY-521 pad map (8 pads) & wiring to the TriBoard

The breakout carries the MPU-6050, an onboard 3.3 V LDO (VCC → chip VDD) and
SDA/SCL pull-ups referenced to the regulated 3.3 V rail.

| Pad | Meaning | Wire to | Header / iLLD object |
|---|---|---|---|
| **VCC** | supply in (→ onboard LDO) | **+3V3 rail** (see §3) | — |
| **GND** | ground | header GND | — |
| **SCL** | serial clock | **P13.1** | X702·29 · `IfxI2c0_SCL_P13_1_INOUT` |
| **SDA** | serial data | **P13.2** | X702·35 · `IfxI2c0_SDA_P13_2_INOUT` |
| **XDA** | auxiliary I2C master data | leave open | (for an external mag) |
| **XCL** | auxiliary I2C master clock | leave open | (for an external mag) |
| **AD0** | address LSB | **GND** (or open) → `0x68` | address select (§4) |
| **INT** | data-ready interrupt | leave open for now | polled at 50 Hz |

Both I2C pads run in a **TTL pad-driver mode** (VIH ≈ 2.0 V) so the 5 V VEXT
port domain still reads the 3.3 V bus — see `PINNING.md` §2.5. Already configured
by `I2c_init()` for the barometer; the IMU inherits it.

---

## 3. Power — VCC at 3.3 V, and bus loading

Feed **VCC from the board's regulated +3V3 rail** (the same rail as the BMP388),
**not** VCC_IN (3.5–40 V) and **not** V_UC (5 V). On the GY-521 the SDA/SCL
pull-ups reference the breakout's regulated 3.3 V, so powering VCC at 3.3 V keeps
the whole bus at a clean 3.3 V that the TC399 TTL pads read reliably. (Most GY-521
LDOs run happily from a 3.3 V input; if a particular clone's LDO dropout starves
it, feed VCC 5 V instead — the pull-ups still reference the internal 3.3 V, so the
bus voltage is unchanged. Prefer 3.3 V.)

**Bus loading:** two devices now pull the bus — BMP388/CJMCU-388 (~10 kΩ) and
GY-521 (~4.7 kΩ) in parallel ≈ **3.2 kΩ** to 3.3 V, ~1 mA sink. Well within the
pad limit, and it sharpens the edges slightly. No external pull-ups needed.

## 4. Interface & address (Register Map §4.32 WHO_AM_I)

- **AD0 sets the address LSB.** GY-521 boards pull AD0 low on-board, so it
  defaults to **`0x68`**:
  - AD0 → **GND** (or left open) → `0x68`  ← driver default (`MPU6050_I2C_ADDR`)
  - AD0 → **3V3** → `0x69`
- Chosen so it never collides with the BMP388 (`0x77`). If both a barometer and a
  second I2C device ever need `0x68`, move one with AD0.
- **WHO_AM_I (0x75) returns `0x68`** on a genuine MPU-6050. Some GY-521 clones
  carry an MPU-6500 / MPU-9250 die that answers **`0x70` / `0x71`** — if the
  bring-up print shows one of those, the chip is a clone: the register map is
  compatible for the accel/gyro burst used here, but update
  `MPU6050_WHO_AM_I_VALUE` to match so `init()` passes.

## 5. Configuration the driver applies (RM-MPU-6000A)

Init order: **DEVICE_RESET → wake → configure.** No `SIGNAL_PATH_RESET` — the
device reset already resets the signal paths, and the known-good Arduino
reference does not issue one. See §7 before changing any of these steps.

| Register | Value | Meaning |
|---|---|---|
| `PWR_MGMT_1` (0x6B) | `0x00` | clear SLEEP, CLKSEL = 0 internal osc (**proven on HW**, see §7) |
| `SMPLRT_DIV` (0x19) | `0x09` | 1 kHz / (1+9) = **100 Hz** internal update |
| `CONFIG` (0x1A) | `0x03` | DLPF ~44 Hz — rejects motor/frame vibration |
| `GYRO_CONFIG` (0x1B) | `0x18` | FS_SEL 3 → **±2000 °/s** (16.4 LSB/°/s) |
| `ACCEL_CONFIG` (0x1C) | `0x10` | AFS_SEL 2 → **±8 g** (4096 LSB/g) |

Sample burst (0x3B, 14 bytes, **big-endian**): accelX/Y/Z, temp, gyroX/Y/Z.
Scaling: accel = raw/4096 g, gyro = raw/16.4 °/s, temp = raw/340 + 36.53 °C.

Change ranges by editing the `*_CONFIG_VAL` / `*_FULLSCALE` pairs in `Mpu6050.c`
(the scale constants derive from the full-scale, so they track automatically).

## 6. Bring-up milestones

1. **WHO_AM_I** — `Mpu6050_readWhoAmI()` returns **`0x68`**. Proves pins, TTL pads,
   pull-ups, address and driver in one transaction. UART prints
   `MPU-6050 detected (WHO_AM_I 0x68)`; a miss prints the wiring/address hint.
2. **Configure + raw read** — wake, ±8 g / ±2000 °/s, DLPF 44 Hz, 100 Hz ODR.
3. **Live in the GUI** — accel/gyro/temp appear on the XCP **Live Data** tab
   (`ImuAccelX…`, `ImuGyroX…`, `ImuTemperature`, firmware ≥ v1.10.0). Sanity at
   rest: **|accel| ≈ 1 g** total (Z ≈ ±1 g flat), **gyro ≈ 0 °/s**, temp roughly
   room temperature +a few °C of self-heating.

**Pre-hardware test (no sensor wired):** the firmware must boot, blink, keep
Ethernet/XCP up, and the GUI must show IMU **"n/a (not detected)"** — proving the
I2C no-ACK path (`I2c.c` bounded retry) fails fast instead of hanging.

## 7. Root cause of the all-zero / frozen readings (SOLVED 2026-07-30)

**Symptom.** `WHO_AM_I` = `0x68`, config readback exact (`09 03 18 10`), every
transfer ACKs — but the whole 14-byte burst at `0x3B`, **including `TEMP_OUT`**,
reads `0x00` forever. In a variant of the fault the burst held *plausible* values
that never changed, no matter how the board was moved.

**Root cause: the I2C master never generated a STOP condition.** iLLD's
`IfxI2c_I2c_initConfig()` defaults `addrFifoCfg.addressConfig.stopOnPacketEnd`
(the module SOPE bit) to **0** — *"after transfer go into master restart state"*.
Every transfer ended with the master still owning the bus. The per-device
`IfxI2c_I2c_deviceConfig.enableRepeatedStart` field looks like it controls this,
but `IfxI2c_I2c_read2()` / `write2()` **never read it**; only the module bit
matters. So `I2c.c` produced repeated starts forever and no STOP.

The MPU-6050 holds its sensor data registers static while a read burst is in
progress, so a burst cannot tear. Never seeing a STOP, it stayed permanently
"mid-read" and **froze the registers at whatever the first read latched**:

- first read after a `DEVICE_RESET` → registers still `0x00` → **frozen at zero
  forever** → looks exactly like a dead MEMS die;
- first read without a reset → a real sample → **frozen at plausible values**.

Fix: `config.addrFifoCfg.addressConfig.stopOnPacketEnd = 1;` in `I2c_init()`.

**Why the BMP388 masked it.** The barometer has no such read-hold behaviour, so
it worked perfectly on the same broken bus and made the bus look proven.

**Verified 2026-07-30** (fw v1.11.0): live streaming, |a| = 0.997 g at rest,
temperature 28.6 °C drifting, accel/gyro LSB noise, tracks movement.

### Things that were wrongly blamed along the way

Recording these so they are not re-investigated:

| Suspect | Verdict |
|---|---|
| "Two dead / counterfeit GY-521 chips" | **Wrong.** The same chip streamed fine on an Arduino. |
| `CLKSEL` (internal osc vs gyro PLL) | Not the cause. `CLKSEL = 0` is proven good here — the working Arduino sketch uses it. |
| `SIGNAL_PATH_RESET` ordering | Not the cause. Removing it changed nothing. |
| `USER_CTRL` / aux-master stall | Not the cause. Measured `0x00` throughout. |
| `DEVICE_RESET` | Not the cause, but it *was* the trigger that made the frozen value be zero. Harmless once STOP works. |
| Supply / VDD brown-out | Not the cause. Bus stayed at 3.3 V with VCC at 5 V. |
| Range / DLPF / sample-rate config | Not the cause. Failed identically with Arduino-default values. |

### Lessons

1. **"An awake MPU always gives non-zero temperature, so the die is dead" is
   invalid reasoning.** The I2C register interface is clocked from **SCL** and
   answers perfectly with no internal clock running. Healthy bus + config sticks
   + all data zero means a **stalled sample path**, never "dead die".
2. **Cross-check on a second MCU early.** A five-minute Arduino sketch exonerated
   the chip after two boards had been written off as counterfeit.
3. **Distinguish "zero" from "frozen".** Sampling repeatedly while moving the
   board is what separated a stalled sensor from a stalled *transaction*, and it
   is what pointed at the bus rather than the chip.
4. **Don't trust a config field because it has the right name.** The
   `enableRepeatedStart` field was set, reviewed, and documented in a header
   comment — and was dead code the whole time.

## 8. Bus recovery (added with the same fix)

`I2c_init()` now bit-bangs a recovery sequence *before* handing P13.1/P13.2 to
the I2C module: up to 9 SCL pulses until SDA is released, then a manual STOP
(I2C-bus spec UM10204 §3.1.16).

Needed because the sensors are polled at 50 Hz and a CPU-only reset (debugger
`-start on`, the board RESET button, a watchdog) can land mid-transfer. The MCU
restarts but the breakouts stay powered, so the slave is still clocking out a
byte and holds SDA low forever. Symptom: **every** device reports "not found"
after a warm reset but works again after a power cycle. Without this, any
debugger-driven reset makes the whole sensor bus look dead.
