How a value travels through the stack

One number — a die temperature, a calibration limit — is wrapped, shipped, and unwrapped through seven layers between the TriCore and the PC. Each layer only talks to the one below it. Here is the whole path, and who owns each rung.

Two directions, same layers

The round trip

The measurement falls down the TriCore stack and climbs the PC stack; the calibration does the reverse and lands back in the memory the diagnostics read.

Measurement out

DAQ · pushed every 100 ms

  • Sensor read → g_xcpData.dieTempC in RAM
  • xcpDaqCycle copies the configured bytes into a DTO
  • Wrapped: XCP → UDP → IP → Ethernet
  • DMA → MAC → PHY → wire
  • PC unwraps each layer, unpack('<f') via the A2L → 59.2 °C on screen

Calibration in

DOWNLOAD · on demand

  • Engineer types a limit in the GUI
  • Wrapped & sent to :5555; DMA lands it in RAM, ISR flags it
  • Loop polls → lwIP → xcpRecv
  • xcpWriteAllowed checks the address → memcpy into g_xcpCal
  • Next 100 ms: diagnosticsUpdate reads the new limit → status bit
The one idea under all of it: XCP moves raw memory bytes by address — no layer between the RAM block and the wire knows a temperature from a voltage. The meaning lives entirely in the A2L file on the PC. That separation is why the same tiny stack can measure, calibrate, and report faults without a line of value-specific networking code.
